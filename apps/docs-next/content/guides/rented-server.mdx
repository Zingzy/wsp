# A rented server

This guide adds a server that you rent from a hosting company to wsp, over ssh. After that, threads run on the server in its own project folders, and you work with them in the app on your own computer. The host stays on your computer. The server runs only the wsp daemon.

## Before you start

The server must have:

- Linux on `x86_64` or `aarch64`. A Mac cannot be a box.
- systemd, and cgroup v2 with the `memory` and `cpu` controllers.
- The overlay filesystem in its kernel.
- Node 22 or newer, for the `wsp` command that sits beside the daemon.
- A root login over ssh with a key that works without a password. wsp runs threads on a box only as root.
- Root's login shell set to bash or sh.
- Free space on `/opt/wsp` for the base tools, plus 1 GiB.

On your computer, you need wsp and a running host. The app starts the host. Without the app, a `wsp` command starts one by itself.

## Step 1: Read the server's host key on the server itself

The first time wsp dials a server, it shows the server's host key and asks you to trust it. If a stranger controls the route during that first dial, wsp records the stranger as your own box. So compare the key with one that you read on the server itself.

Do not test the login with `ssh` first, or your ssh client stores the key and `wsp add` asks nothing.

Open a shell on the server through the web console of your hosting company, and run:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
node --version
```

Keep the `SHA256:` fingerprint for step 2. If the version is below `v22`, install Node 22 or newer with the server's package manager. Also make sure that your public key is in `/root/.ssh/authorized_keys`.

If your ssh client already connected to this server once, `wsp add` asks nothing. Compare the key that your computer holds with the fingerprint from the server:

```sh
ssh-keygen -l -F 203.0.113.7
```

## Step 2: Add the server

You can add the server in the app or on the command line.

In the app, open Settings > Computers and click Add a computer. Pick the server from the hosts in your ssh configuration, or type `root@203.0.113.7`. Then go through the steps of the dialog.

<Image src="/shots/wizard-00-where.webp" alt="The first step of Add a computer: the hosts from your ssh configuration, and a field for a new address" />

On the command line, name the server:

```sh
wsp add root@203.0.113.7 --name vps
```

wsp asks about the host key:

```
root@203.0.113.7 answers with the key ssh-ed25519 SHA256:...; trust it and continue?
```

Compare the fingerprint with the one from step 1. Answer `yes` only if they are the same.

If you run the add without a terminal, for example from an agent, wsp cannot ask. Give the key on the line instead:

```sh
wsp add root@203.0.113.7 --name vps --host-key 'SHA256:...'
```

`--host-key` takes the fingerprint alone or the whole `ssh-ed25519 SHA256:...` word. If the server answers with another key, the add stops before it sends anything. ssh has still saved that other key, and a second add without `--host-key` trusts it without asking. So before you add the server again, run the `ssh-keygen -R` line that the add prints.

Other flags of the add:

- `--recipe <name>` sets the server up from a saved recipe. Step 4 shows how to save one.
- `--ssh-port <port>` for an ssh port other than 22.
- `--ssh-key <path>` for a key that your ssh configuration does not name.
- `--later` to go past sign-ins that wait for you, and finish them afterwards.

## Step 3: Watch the install

The add prints each step as it goes:

```
connecting over ssh
remembering the box's host key in ~/.ssh/known_hosts
checking it can run wsp
reading its chip and system
checking it logs in as root
checking for systemd and cgroup v2
checking it has room for the base tools
checking it can reach this computer
installing wsp
starting the agent
waiting for it to connect to this computer
```

When the server joins, the add prints:

```
vps joined this wsp, 4 cores, 8 GB, 61 GB free
its ssh key      ssh-ed25519 SHA256:...
wsp remove vps takes it back out and sweeps wsp off it.
```

## Step 4: Choose what goes on the server

A recipe is the list of agents, tools, MCP servers, skills, plugins and configuration that a computer gets. [Recipes](/features/recipes) shows them in the app.

Without `--recipe`, the base tools go on, and the server waits for you to choose the rest:

```
vps waits on what goes on it, with the base tools going on meanwhile: choose in the app's Add a computer, or run wsp add vps --resume --recipe <name>
```

Choose in the app's Add a computer. When the server is set up, save its picks as a recipe, so that your next box can take the same list:

```sh
wsp recipes save mine --from vps
wsp add root@198.51.100.4 --name vps2 --recipe mine
```

After the save, vps follows `mine`. When `mine` changes later, wsp applies the change to every computer that follows it. `wsp recipes` lists the recipes that you saved. You cannot save a recipe from the computer that the app runs on.

If one step of the setup fails, the setup says why and goes on with the others. Only a failed base tools step or agents step stops it.

## Step 5: Sign in on the server

The agents and gh sign in on the server, not on your computer. When a sign-in waits for you, the add prints a line with the page and the code, and it opens the page in your browser:

```
  ? GitHub waits on you to sign in at https://github.com/login/device with code 8F4A-C21B
```

Sign in in your browser, and the add goes on. If you used `--later`, run `wsp add vps --resume` to finish the sign-ins. [How sign-ins reach your browser](/how/sign-ins) explains the path of the page.

## Step 6: Add a project and start a thread

Clone a repo on the server as a project:

```sh
wsp add https://github.com/acme/api --on vps
```

`wsp projects` lists the project with its name. Start a thread on it by that name:

```sh
wsp run api "Read the README and run the tests."
```

The thread runs in the project's folder on the server, as root, and it shows in your sidebar.

## If the server cannot reach your computer

The daemon on the server dials your host. A rented server usually cannot reach a computer at your home or office, so the daemon dials back over the ssh connection instead, and the install says `dials back over ssh`. The server's sshd must allow TCP forwarding, which it does by default.

If that fails too, the add stops before it installs anything. Link your host to the relay with `wsp host link`, as [A box behind a firewall](/guides/behind-a-firewall) shows, and add the server again.

## Set how many threads run at once

By default, a box runs one thread at once for each 2 GB of memory. To change it:

```sh
wsp computers set vps --threads 4
```

A thread over the limit waits and starts by itself. It says why it waits:

```
waiting while vps is running 2 of 2 threads
```

In the app, the waiting thread has a **Raise threads at once** button. `wsp computers set vps --reset threads` goes back to the default.

## Update and remove the server

When the host is newer than the daemon on the server, the server's row says so. To update the daemon:

```sh
wsp add vps --update
```

To take wsp off the server:

```sh
wsp remove vps
```

The remove asks first. It stops if work on the server is not pushed to a remote, unless you add `--force`. It deletes wsp's files on the server and leaves your project folders.
